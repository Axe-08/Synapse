## 1. Introduction

### 1.1 Purpose

This Software Requirements Specification (SRS) documents the complete requirements for **Project Synapse v2.0**, a resilient, self-tuning, **distributed** multi-stage automated data pipeline. It generates a high-fidelity, verified dataset of competitive programming problems with reference solutions, language-agnostic pseudocode, and reconstructed C++ implementations for AI training.

**Key changes from v1.0:**
- Hybrid compute architecture (laptop + DGX server)
- PostgreSQL database backend with SQLite fallback
- Intelligent optimizer with API budget and scraper telemetry
- AI-generated test suite (fuzz generator)
- CF Submission Worker for interactive/special judge problems
- Problem classification and routing
- Dynamic thread pool scaling with backpressure

### 1.2 Scope

Project Synapse ingests problems from **Codeforces**, processes them through LLM-powered stages, and verifies outputs using a sandboxed execution environment. The system operates across **two physical machines**:

- **Laptop** — ingestion node (web scraping via Chrome/Selenium)
- **DGX Server** — processing node (calibration, analysis, implementation, VJS, assembly)

Both machines communicate through a shared **PostgreSQL 16** database. The final output is a JSONL dataset versioned via DVC.

### 1.3 Definitions, Acronyms, Abbreviations

| Term | Definition |
|------|------------|
| **ARL** | Algorithm Representation Layer — the Analysis + Implementation stage pair |
| **VJS** | Verification & Judging Subsystem — the Docker-based code judge |
| **DAL** | Data Access Layer — `database.py` module with PG/SQLite adapter |
| **DVC** | Data Version Control |
| **Data Manager** | Utility module (`data_manager.py`) handling append operations to the final dataset |
| **Status Monitor** | Terminal live dashboard utility (`status.py` + `stats_monitor.py`) |
| **Shared Defaults** | Common imports for worker threads (`workers/_shared.py`) |
| **Oracle** | A verified reference C++ solution scraped from Codeforces |
| **Fuzz Generator** | AI-generated Python script that produces random valid test inputs |
| **Golden Record** | The final assembled data record for a successfully processed problem |
| **Pretest** | A judge test case (input/output pair) used to verify a solution |
| **Pseudocode** | Language-agnostic algorithm representation generated by the Analyst LLM |
| **Backpressure** | Throttling upstream stages when downstream queues are overloaded |
| **RPM/RPD** | Requests Per Minute / Requests Per Day (API rate limits) |
| **TPM/TPD** | Tokens Per Minute / Tokens Per Day (API token limits) |
| **DGX** | NVIDIA DGX server — shared university compute resource |

## 2. Overall Description

### 2.1 Product Perspective

Project Synapse is a **distributed**, command-line, multi-process Python application. It is **not** a web service or UI application. It interacts with:

- **Codeforces** (external): Source of problems and solutions
- **Google Gemini API** (external): Analyst LLM for pseudocode + test generator script
- **Groq API** (external): Implementer LLM for C++ code reconstruction
- **Docker** (local to DGX): Sandboxed code execution and judging
- **PostgreSQL 16** (DGX): Primary shared database (production)
- **SQLite** (local): Fallback database (development/testing)
- **DVC Remote Storage** (optional): Dataset versioning backup
- **SSH Tunnel** (network): Laptop → DGX database connectivity

### 2.2 Product Functions (High Level)

1. **Automatic Problem Ingestion** — Scrape full problem data from Codeforces (laptop)
2. **Problem Classification** — Classify problems as standard/special/interactive/constructive
3. **Multi-Oracle Calibration** — Validate N reference solutions and establish baselines (DGX)
4. **Oracle Crash Pre-filter** — Discard truncated/corrupted pretests via oracle validation
5. **LLM-Powered Analysis** — Convert C++ oracles to pseudocode + fuzz generator (Gemini)
6. **LLM-Powered Implementation** — Reconstruct C++ code from pseudocode (Groq/DeepSeek)
7. **Sandboxed Verification** — Compile and judge AI code using combined test suite (pretests + generated)
8. **CF Submission Verification** — Submit code to Codeforces for interactive/special judge problems
9. **Intelligent Retry Routing** — Route failures to the correct LLM with structured feedback
10. **Data Assembly** — Assemble and enrich final golden records with quality metadata
11. **Intelligent Optimizer** — Dynamically adjust workers based on queue depth, API budget, DGX load, and scraper health
12. **Live Monitoring** — Real-time status dashboard with API budget and scraper telemetry

### 2.3 User Classes and Characteristics

| User Class | Description |
|-----------|-------------|
| **Pipeline Operator** | Runs and monitors the pipeline; configures `.env`; resolves CAPTCHAs; manages DGX deployment |
| **Data Consumer** | Uses the final `dataset.jsonl` for AI/ML training |
| **Developer** | Extends or debugs pipeline stages; reads logs |

### 2.4 Operating Environment

**Laptop (Ingestion Node):**
- **OS:** Linux
- **Python:** 3.10+
- **Browser:** Google Chrome (for undetected-chromedriver Selenium)
- **Network:** SSH tunnel to DGX for PostgreSQL access

**DGX Server (Processing Node):**
- **OS:** Linux (shared NVIDIA DGX)
- **Python:** 3.x (via Docker container)
- **Docker:** v26.x (shared Docker daemon)
- **PostgreSQL:** 16 (in Docker container)
- **Resources:** Shared — must be a courteous user

### 2.5 Design and Implementation Constraints

- **Hybrid Architecture:** Ingestion runs only on laptop; processing runs only on DGX
- **Shared Resource Courtesy:** DGX is a university resource — optimizer must monitor system load and yield when CPU > 70%
- **Free Tier API Limits:** All API usage must respect RPM/RPD/TPM/TPD limits; no paid tiers assumed
- **PostgreSQL for production;** SQLite for development and testing
- **Git-based deployment:** Code is pushed via `git push`, pulled on DGX via `make dgx-pull`
- **No inbound ports** on DGX — all communication via shared PostgreSQL
- Docker must be available on DGX; `synapse-judge` image must be pre-built
- Credentials stored in `.env` file, never committed

## 3. System Features & Functional Requirements

### 3.1 Stage 1: Problem Ingestion (Laptop Only)

**Description:** Fetches all necessary raw data for a problem from Codeforces. Runs exclusively on the laptop via `ingestion_node.py`.

| ID | Requirement |
|----|-------------|
| FR-1.1 | The system SHALL use `requests` (HTTP) for public-facing problem pages |
| FR-1.2 | The system SHALL use an authenticated `undetected-chromedriver` instance to scrape source code from protected submission pages |
| FR-1.3 | The system SHALL scrape up to `N_REFERENCE_SOLUTIONS` (default: 5) top-rated accepted C++ submissions per problem |
| FR-1.4 | The system SHALL attempt to enrich example pretests using Codeforces' internal API |
| FR-1.5 | The system SHALL detect IP ban responses and raise an `IPBanException` |
| FR-1.6 | The system SHALL classify problems at ingestion time (see §3.2) |
| FR-1.7 | The system SHOULD reuse browser instances (up to `MAX_BROWSER_USES=25` times) |
| FR-1.8 | The system SHALL support re-scraping to find new reference solutions on retry |
| FR-1.9 | The system SHALL record scraper telemetry per account to the `scraper_stats` table |
| FR-1.10 | The system SHALL support multiple scraper accounts with automatic rotation on ban detection |

### 3.2 Problem Classification

**Description:** At ingestion time, classify each problem using CF API metadata + statement parsing to determine the pipeline routing path.

| ID | Requirement |
|----|-------------|
| FR-2.1 | The system SHALL detect interactive problems via `type: INTERACTIVE` from CF API |
| FR-2.2 | The system SHALL detect special judge problems via CF tags or "you may print any" in statement |
| FR-2.3 | The system SHALL detect constructive problems via "output any valid" in statement |
| FR-2.4 | The system SHALL store `problem_class` in the `problems` table |
| FR-2.5 | Interactive problems SHALL skip VJS and route directly to CF Submission Worker |
| FR-2.6 | Standard problems SHALL follow the full local VJS pipeline |

### 3.3 Stage 2: Calibration (DGX)

**Description:** Validates scraped reference solutions by compiling them in Docker and establishes performance baselines.

| ID | Requirement |
|----|-------------|
| FR-3.1 | The system SHALL compile each oracle using Docker-based VJS (`compile_only` mode) |
| FR-3.2 | The system SHALL require at least `MIN_VIABLE_ORACLES` (default: 3) compilations to proceed |
| FR-3.3 | The system SHALL quarantine a problem if fewer than `MIN_VIABLE_ORACLES` oracles compile |
| FR-3.4 | The system SHALL run the primary oracle against pretests to calculate a `slowness_factor` |
| FR-3.5 | The system SHALL detect set-based output problems and set `checker_mode = 'set_based'` |
| FR-3.6 | The system SHALL validate pretests via oracle crash detection — discarding truncated/corrupted inputs |
| FR-3.7 | Pretests where any oracle crashes, times out, or oracles disagree SHALL be discarded |

### 3.4 Stage 3: Analysis (Gemini LLM — Analyst, DGX)

**Description:** Sends problems to the Gemini API with structured output schema to produce canonical pseudocode and a test generator script.

| ID | Requirement |
|----|-------------|
| FR-4.1 | The system SHALL send batches (default size: 5) of problems in a single API call |
| FR-4.2 | The system SHALL preprocess C++ code before sending (strip comments, boilerplate) |
| FR-4.3 | The system SHALL select and send the top 3 highest-quality oracle solutions per problem |
| FR-4.4 | The system SHALL use Gemini 2.5 Pro with JSON schema enforcement (structured output) |
| FR-4.5 | The Gemini response SHALL include `pseudocode`, `input_generator_py`, and `oracle_quality_ratings` |
| FR-4.6 | The system SHALL include `problem_class`, `rating`, and `tags` in the analysis prompt context |
| FR-4.7 | The system SHALL include the last VJS failure report in retry prompts |
| FR-4.8 | The system SHALL quarantine a problem if `analysis_try_count >= MAX_ANALYSIS_RETRIES` (default: 3) |
| FR-4.9 | The system SHALL store `input_generator_py` in `problem_data_cache` for VJS |

### 3.5 Stage 4: Implementation (Groq LLM — Implementer, DGX)

**Description:** Sends pseudocode to the Groq API to reconstruct a complete C++ solution.

| ID | Requirement |
|----|-------------|
| FR-5.1 | The system SHALL call the Groq API (DeepSeek-V3.2) with problem HTML, pseudocode, and VJS report |
| FR-5.2 | The system SHALL sanitize the LLM output to strip markdown formatting from raw code |
| FR-5.3 | The system SHALL run `g++ -fsyntax-only` pre-check before committing to VJS |
| FR-5.4 | Syntax check failures SHALL feed back to the Implementer immediately (without entering VJS queue) |
| FR-5.5 | The system SHALL quarantine a problem if `implementation_try_count >= MAX_IMPLEMENTATION_RETRIES` (default: 5) |
| FR-5.6 | The system SHALL apply temperature escalation on retries (`GROQ_TEMPERATURE_RETRY_INCREMENT`) |

### 3.6 Stage 5: Verification & Judging (VJS, DGX)

**Description:** Compiles and judges AI-generated code inside a Docker sandbox against a **combined test suite** of oracle-validated pretests and AI-generated fuzz tests.

| ID | Requirement |
|----|-------------|
| FR-6.1 | The system SHALL run all compiled oracle binaries in parallel to generate golden expected outputs |
| FR-6.2 | The system SHALL determine consensus via tiered weighted-vote mechanism |
| FR-6.3 | Oracle weights SHALL be based on Gemini quality ratings: Excellent=4, Good=3, Fair=2, Poor=1 |
| FR-6.4 | The system SHALL execute the `input_generator_py` script N times (default: 20) to generate synthetic inputs |
| FR-6.5 | Generated inputs SHALL be fed through all oracles; inputs where any oracle crashes SHALL be discarded |
| FR-6.6 | Inputs where all oracles agree on output SHALL be added to the test suite with the consensus output as expected |
| FR-6.7 | The combined test suite = validated pretests + validated generated tests |
| FR-6.8 | The system SHALL compile AI code in Docker with `g++ -O2 -std=c++23 -static` |
| FR-6.9 | Compilation failure SHALL route back to `pending_implementation` with compiler stderr |
| FR-6.10 | Runtime failure or Wrong Answer SHALL route back to `pending_analysis` with a detailed failure report |
| FR-6.11 | On VJS success, `confidence_level` SHALL be set to 2 |

### 3.7 Stage 6: CF Submission Worker (DGX)

**Description:** Submits fabricated code to Codeforces using burner accounts. Used for interactive problems and special judge problems where local VJS cannot provide ground truth.

| ID | Requirement |
|----|-------------|
| FR-7.1 | The system SHALL maintain a pool of submission accounts, rotated round-robin |
| FR-7.2 | The system SHALL submit code via Selenium to `codeforces.com/contest/{id}/submit` |
| FR-7.3 | The system SHALL poll for verdict every 5s, up to 5min timeout |
| FR-7.4 | `Accepted` verdict SHALL transition to `pending_data_assembly` |
| FR-7.5 | `Wrong Answer (test N)` SHALL route back to `pending_analysis` with test number feedback |
| FR-7.6 | `TLE` SHALL route back to `pending_implementation` with complexity hint |
| FR-7.7 | `Compile Error` SHALL route back to `pending_implementation` with compiler stderr |
| FR-7.8 | Timeout / `System Error` SHALL quarantine the problem |
| FR-7.9 | Rate limit: ~10 submissions/hour/account |

### 3.8 Stage 7: Data Assembly (DGX)

**Description:** Assembles the final golden record and writes it to the output dataset.

| ID | Requirement |
|----|-------------|
| FR-8.1 | The system SHALL assemble a complete JSON record including: problem metadata, HTML statement, pseudocode, reference code, reconstructed code, pretests, code quality metrics, confidence metadata |
| FR-8.2 | Code quality metrics SHALL include cyclomatic complexity (via `lizard`) |
| FR-8.3 | Confidence metadata SHALL include: `truncation_rate`, `fuzz_test_count`, `cf_submission_verdict` |
| FR-8.4 | The system SHALL deduplicate records via SHA256 hash of `(problem_id, pseudocode)` |
| FR-8.5 | The assembled record SHALL be appended to `dataset.jsonl` |
| FR-8.6 | The problem's workspace data SHALL be deleted after successful assembly |
| FR-8.7 | The problem status SHALL be set to `completed` |

### 3.9 Intelligent Optimizer

**Description:** A module inside the pipeline container that monitors system state and dynamically adjusts worker counts, API pacing, and scraper behavior.

#### 3.9.1 Optimizer Inputs

| ID | Requirement |
|----|-------------|
| FR-9.1 | The optimizer SHALL read queue depths per stage from `problems` table |
| FR-9.2 | The optimizer SHALL read DGX CPU utilization via `psutil.cpu_percent()` |
| FR-9.3 | The optimizer SHALL read DGX RAM utilization via `psutil.virtual_memory()` |
| FR-9.4 | The optimizer SHALL read per-stage average processing duration from `metrics` table |
| FR-9.5 | The optimizer SHALL read API budget status from `KeyManager` (requests/tokens remaining per key per day/minute) |
| FR-9.6 | The optimizer SHALL read scraper telemetry from `scraper_stats` table |
| FR-9.7 | The optimizer SHALL read historical DGX usage patterns from `dgx_usage_stats` table |

#### 3.9.2 Optimizer Decision Rules

| ID | Requirement |
|----|-------------|
| FR-9.8 | Stages with 0 pending jobs SHALL have workers set to 0 (stage skipping) |
| FR-9.9 | When DGX CPU > 70%, the optimizer SHALL scale all workers down by 50% (courtesy mode) |
| FR-9.10 | When DGX CPU < 20%, the optimizer SHALL scale up based on queue depth (burst mode) |
| FR-9.11 | When a downstream stage queue > 2× upstream queue, the optimizer SHALL throttle the upstream stage (backpressure) |
| FR-9.12 | When API tokens_today > 90% of TPD limit, the optimizer SHALL reduce workers for that API to 1 |
| FR-9.13 | When API tokens_today > 98% of TPD limit, the optimizer SHALL set workers for that API to 0 |
| FR-9.14 | When requests_this_minute > 80% of RPM limit, the optimizer SHALL pause the stage for 10 seconds |
| FR-9.15 | IP ban detection SHALL set `ingestion_worker_count = 0` for 2 hours (PANIC MODE) |
| FR-9.16 | The optimizer SHALL use historical usage patterns to identify low-usage windows for burst processing |
| FR-9.17 | All optimizer actions SHALL respect a cooldown period between adjustments |

#### 3.9.3 Optimizer Outputs

| ID | Requirement |
|----|-------------|
| FR-9.18 | The optimizer SHALL write updated worker counts to `dynamic_config` table |
| FR-9.19 | The optimizer SHALL log usage snapshots to `dgx_usage_stats` every 5 minutes |
| FR-9.20 | The optimizer SHALL log scraper stats events (ban, success, rate) |

### 3.10 KeyManager & API Budget Tracking

| ID | Requirement |
|----|-------------|
| FR-10.1 | The system SHALL support multiple API keys for both Gemini and Groq services |
| FR-10.2 | The system SHALL track per-key: `requests_today`, `requests_this_minute`, `tokens_today`, `tokens_this_minute` |
| FR-10.3 | The system SHALL parse `x-ratelimit-remaining-*` headers from Groq API responses |
| FR-10.4 | Rate-limited keys (429 responses) SHALL be placed in cooldown |
| FR-10.5 | Invalid keys SHALL be permanently marked and excluded |
| FR-10.6 | `KeyManager.get_budget_status(service)` SHALL return remaining RPM/RPD/TPM/TPD headroom |
| FR-10.7 | `KeyManager.should_throttle(service)` SHALL return true when approaching rate limits |
| FR-10.8 | A background `KeyHealthMonitor` thread SHALL periodically reset time-windowed counters |

### 3.11 Scraper Account Manager & Telemetry

| ID | Requirement |
|----|-------------|
| FR-11.1 | The system SHALL support multiple Codeforces accounts for scraping, rotated automatically |
| FR-11.2 | Each account SHALL maintain its own `chrome_profile_{handle}/` for persistent sessions |
| FR-11.3 | The system SHALL track per-account: `total_requests`, `successful_scrapes`, `blocks_count`, `last_block_at`, `last_unblock_at`, `requests_since_last_block` |
| FR-11.4 | The system SHALL calculate `safe_request_rate` per account from ban history |
| FR-11.5 | Ban detection SHALL trigger preemptive rotation to the next available account |
| FR-11.6 | Accounts in cooldown SHALL not be used until `avg_ban_duration` has elapsed |

### 3.12 Live Status Dashboard

| ID | Requirement |
|----|-------------|
| FR-12.1 | The dashboard SHALL display real-time queue sizes for each pipeline stage |
| FR-12.2 | The dashboard SHALL display active workers per stage with current problem ID |
| FR-12.3 | The dashboard SHALL display optimizer lever values |
| FR-12.4 | The dashboard SHALL display API budget status (RPD/TPD usage bars per service) |

## 4. Non-Functional Requirements

### 4.1 Performance

| ID | Requirement |
|----|-------------|
| NFR-1.1 | The pipeline SHALL process multiple problems concurrently using dynamic `ThreadPoolExecutor` per stage |
| NFR-1.2 | VJS oracle runs SHALL be parallelized using an inner `ThreadPoolExecutor` |
| NFR-1.3 | All database write operations SHALL be serialized via the `DatabaseWriter` queue |
| NFR-1.4 | PostgreSQL connections SHALL use `FOR UPDATE SKIP LOCKED` for lock-free job claiming |
| NFR-1.5 | Assembly records SHOULD be batched (every 10 minutes) to reduce I/O overhead |

### 4.2 Reliability & Fault Tolerance

| ID | Requirement |
|----|-------------|
| NFR-2.1 | The pipeline SHALL be fully resumable — restarting SHALL not cause data loss or duplicates |
| NFR-2.2 | All state transitions SHALL be atomic database operations |
| NFR-2.3 | Transient database lock errors SHALL be retried up to 5 times with backoff |
| NFR-2.4 | Worker exceptions SHALL be caught, logged, and the problem transitioned to a `failed_*` state |
| NFR-2.5 | Browser instances SHALL be retired after 25 uses |
| NFR-2.6 | Retried problems SHALL have their `priority` incremented so they bubble to the front of the queue |

### 4.3 Security

| ID | Requirement |
|----|-------------|
| NFR-3.1 | All compiled/executed code SHALL run inside Docker with memory limits |
| NFR-3.2 | Docker containers SHALL run as non-root (`--user uid:gid`) |
| NFR-3.3 | Code execution SHALL use read-only volume mounts where possible |
| NFR-3.4 | API credentials SHALL be stored in `.env` files, never committed |
| NFR-3.5 | The SSH tunnel SHALL encrypt all laptop-to-DGX database traffic |

### 4.4 Maintainability

| ID | Requirement |
|----|-------------|
| NFR-4.1 | All parameters SHALL be configurable via `config.py` (static) or `dynamic_config` table (runtime) |
| NFR-4.2 | Each pipeline stage SHALL be implemented as an independent worker in `synapse/workers/` |
| NFR-4.3 | All significant events SHALL be logged to `process_history` table |
| NFR-4.4 | All performance metrics SHALL be logged to the `metrics` table |
| NFR-4.5 | The database adapter SHALL transparently support both SQLite and PostgreSQL |

### 4.5 Scalability & Resource Courtesy

| ID | Requirement |
|----|-------------|
| NFR-5.1 | Worker pool sizes SHALL be dynamically adjustable at runtime |
| NFR-5.2 | The system SHALL monitor DGX CPU usage and scale down when system load is high |
| NFR-5.3 | The optimizer SHALL identify low-usage time windows for burst processing |
| NFR-5.4 | Docker containers on DGX SHOULD use `--cpus` limits during peak hours |

## 5. External Interface Requirements

### 5.1 Codeforces Interactions

| Interface | Method | Auth | Rate Limit |
|-----------|--------|------|------------|
| Problem page | HTTPS GET | Public | Managed by scraper delay |
| Contest status API | HTTPS GET | Public | CF API limits |
| Submission source | Selenium browser | Session cookie | Managed by scraper delay |
| Internal pretests API | Cookie-auth POST | Session cookie | Managed by scraper delay |
| Code submission (CF Worker) | Selenium form submit | Burner account | ~10/hr/account |

### 5.2 Google Gemini API

- **Model:** `gemini-2.5-pro` (structured output with JSON schema)
- **Input:** Structured JSON batch prompt: problem HTML + oracle C++ code + problem_class + VJS report
- **Output:** JSON with enforced schema: `{pseudocode, input_generator_py, oracle_quality_ratings[]}`
- **Auth:** API key from `.env`; managed by `KeyManager`
- **Free Tier Limits:** ~10 RPM, ~1,500 RPD, ~250K TPM, ~2.5M TPD

### 5.3 Groq API

- **Model:** `deepseek-v3.2-speciale` (or latest top-performing code model)
- **Input:** Problem HTML + pseudocode + optional VJS failure report
- **Output:** Raw C++ source code
- **Auth:** API key from `.env`; managed by `KeyManager`
- **Free Tier Limits:** ~30 RPM, ~14,400 RPD, ~6K TPM
- **Rate Limit Headers:** `x-ratelimit-remaining-*` parsed for precise budget tracking

### 5.4 Docker

- **Image:** `synapse-judge` (custom, from `Dockerfile`)
- **Compile command:** `g++ main.cpp -o main -O2 -std=c++23 -static`
- **Execute:** `timeout <T> ./main` with stdin/stdout piped
- **Constraints:** `--memory=<limit>k`, `--ulimit stack=268435456`

### 5.5 PostgreSQL (DGX)

- **Version:** 16 (in Docker container)
- **Connection:** `postgresql://synapse:synapse@localhost:5432/synapse_db`
- **Schemas:** `progress` (pipeline state), `workspace` (intermediate cache)
- **Access:** DGX container via Docker network; laptop via SSH tunnel (`localhost:5432`)
- **Concurrency:** `FOR UPDATE SKIP LOCKED` for atomic job claiming

### 5.6 SSH Tunnel (Laptop → DGX)

- **Command:** `ssh -L 5432:localhost:5432 dgx-jump -N`
- **Purpose:** Maps DGX PostgreSQL port to laptop localhost
- **Used by:** `ingestion_node.py` on the laptop

## 6. System Constraints & Assumptions

### 6.1 Constraints

- DGX is a shared university resource — must not monopolize CPU/memory
- Free tier API limits are hard constraints (no paid plans assumed initially)
- Codeforces may rate-limit or ban scraping accounts at any time
- `synapse-judge` Docker image must be built before first run
- SSH key setup required for `dgx-jump` alias
- No inbound ports on either machine — all communication via shared PostgreSQL

### 6.2 Assumptions

- The operator has at least 2 valid Codeforces credentials
- At least one valid Gemini API key and one Groq API key are provided
- Google Chrome is installed on the laptop
- Docker daemon is running on DGX
- The operator can SSH into DGX (`ssh dgx-jump`)
- The operator will create the `.env` file on DGX manually with API keys

## 7. Database Schema

### 7.1 Backend Selection

The database backend is selected via the `DATABASE_URL` environment variable:
- **Set:** PostgreSQL mode — `postgresql://synapse:synapse@localhost:5432/synapse_db`
- **Unset:** SQLite mode — `progress.db` and `workspace.db` files

The DAL (`database.py`) provides a transparent adapter; callers do not know which backend is active.

### 7.2 `progress` Schema — Pipeline State

#### Table: `problems`

| Column | Type | Description |
|--------|------|-------------|
| `id` | TEXT PK | Problem ID (e.g., `1234A`) |
| `contest_id` | INTEGER | Codeforces contest ID |
| `problem_index` | TEXT | Problem letter/index (e.g., `A`) |
| `rating` | INTEGER | Problem difficulty rating |
| `status` | TEXT | Current pipeline status (see §8) |
| `priority` | INTEGER | Priority queue value — incremented on retries; higher = processed first |
| `problem_class` | TEXT | `standard`, `special_judge`, `interactive`, `constructive` |
| `notes` | TEXT | Failure/quarantine reason |
| `analysis_try_count` | INTEGER | Number of analysis attempts |
| `implementation_try_count` | INTEGER | Number of implementation attempts |
| `rescraping_attempts` | INTEGER | Number of re-scrape attempts |
| `tried_submission_ids` | TEXT | Comma-separated IDs of tried submissions |
| `reference_submissions_json` | TEXT | JSON array of oracle submission objects |
| `successful_oracles` | INTEGER | Count of successfully compiled oracles |
| `confidence_level` | INTEGER | 0=not started, 1=calibrated, 2=vjs_passed |
| `last_vjs_report` | TEXT | Last VJS failure report |
| `submission_account` | TEXT | CF account used for submission (CF worker) |
| `last_updated` | TEXT | ISO timestamp |

#### Table: `live_workers`

| Column | Type | Description |

## 8. Pipeline State Machine

```
pending_ingestion                                           (LAPTOP)
    │
    ▼ (ingestion_worker)
pending_calibration                                         (DGX)
    │
    ▼ (calibration_worker — oracle crash filter)
pending_analysis ◄─────────────────────────────────────────┐
    │                                                       │
    ▼ (analysis_worker — Gemini: pseudocode + generator)    │ (VJS: logic/runtime failure)
pending_implementation ◄────────────────────┐               │
    │                                       │               │
    ▼ (implementation_worker — Groq)        │ (VJS:         │
    │                                       │  compile      │
    ├─── [standard] ──► pending_vjs         │  error)       │
    │                       │               │               │
    │                       ├──────────────►┘               │
    │                       ├──────────────────────────────►┘
    │                       │
    │                       ▼ (vjs_worker — SUCCESS)
    │                   pending_data_assembly ◄──────────────┐
    │                       │                                │
    │                       ▼ (data_assembly_worker)         │
    │                   completed                            │
    │                                                        │
    └─── [interactive/special] ──► pending_cf_submission      │
                                       │                     │
                                       ├── AC ──────────────►┘
                                       ├── WA → pending_analysis
                                       ├── TLE/CE → pending_implementation
                                       └── Timeout → quarantined

At any stage → quarantined (unrecoverable failure)
At any stage → failed_<stage> (transient failure, will be retried with higher priority)
pending_analysis → pending_rescraping → pending_ingestion (re-scrape loop)
```

## 9. Glossary

| Term | Meaning |
|------|---------|
| **Patient Resilience** | Design philosophy of handling long-duration failures gracefully |
| **N-Version Programming** | Using N independent oracle solutions to establish ground truth |
| **Tiered Consensus** | Two-level weighted voting system for oracle output |
| **Oracle Crash Pre-filter** | Validation pass that discards truncated/corrupted pretests using oracle behavior |
| **Fuzz Generator** | AI-generated Python script producing random valid test inputs per problem |
| **PANIC MODE** | Optimizer emergency state triggered by IP ban detection |
| **Courtesy Mode** | Optimizer reduces workers when DGX CPU > 70% (shared resource etiquette) |
| **Burst Mode** | Optimizer maximizes workers during identified low-usage time windows |
| **Backpressure** | Throttling upstream workers when downstream queues are overloaded |
| **Stage Skipping** | Setting worker count to 0 for stages with empty queues |
| **Priority Queue** | Jobs ordered by `priority DESC, rating ASC` — retried problems get higher priority |
| **Quarantine** | Terminal failed state for problems that cannot be processed |
| **Slowness Factor** | Local machine speed multiplier applied to official time limits |
| **Checker Mode** | `strict` (exact match) or `set_based` (unordered match) for output validation |
