## 1. Introduction

### 1.1 Purpose

This Software Requirements Specification (SRS) documents the complete requirements for **Project Synapse**, a resilient, self-tuning, multi-stage automated data pipeline. Its purpose is to generate a high-fidelity, verified dataset of competitive programming problems complete with reference solutions, language-agnostic pseudocode, and reconstructed C++ implementations for AI training use.

### 1.2 Scope

Project Synapse ingests problems from **Codeforces**, a competitive programming platform, processes them through a series of LLM-powered stages, and verifies the outputs using a sandboxed execution environment. The final output is a JSONL dataset (versioned via DVC) suitable for training Large Language Models on algorithmic reasoning tasks.

### 1.3 Definitions, Acronyms, Abbreviations

| Term | Definition |
|------|------------|
| **ARL** | Algorithm Representation Layer — the Analysis + Implementation stage pair |
| **VJS** | Verification & Judging Subsystem — the Docker-based code judge |
| **DAL** | Data Access Layer — `database.py` module |
| **DVC** | Data Version Control |
| **Oracle** | A verified reference C++ solution scraped from Codeforces |
| **AIMD** | Additive Increase / Multiplicative Decrease — a congestion control algorithm |
| **WAL** | Write-Ahead Logging — SQLite concurrency mode |
| **JSONL** | JSON Lines format — one JSON object per line |
| **Pretest** | A judge test case (input/output pair) used to verify a solution |
| **Pseudocode** | Language-agnostic algorithm representation generated by the Analyst LLM |
| **Golden Record** | The final assembled data record for a successfully processed problem |

- Codeforces Public API: `https://codeforces.com/api`
- Google Gemini API Documentation
- Groq API Documentation

## 2. Overall Description

### 2.1 Product Perspective

Project Synapse is a standalone, command-line, multi-process Python application. It is **not** a web service or UI application. It interacts with:

- **Codeforces** (external): Source of problems and solutions
- **Google Gemini API** (external): Analyst LLM for pseudocode generation
- **Groq API** (external): Implementer LLM for C++ code reconstruction
- **Docker** (local): Sandboxed code execution and judging
- **SQLite** (local): Stateful pipeline management
- **DVC Remote Storage** (optional): Dataset versioning backup

### 2.2 Product Functions (High Level)

1. **Automatic Problem Ingestion** — Scrape full problem data from Codeforces
2. **Multi-Oracle Calibration** — Validate N reference solutions and establish performance baselines
3. **LLM-Powered Analysis** — Convert C++ reference solutions to canonical pseudocode (Gemini)
4. **LLM-Powered Implementation** — Reconstruct C++ code from pseudocode (Groq/Llama)
5. **Sandboxed Verification** — Compile and judge AI-generated code in Docker
6. **Intelligent Retry Routing** — Route failures back to the correct LLM with structured feedback
7. **Data Assembly** — Assemble and enrich final golden records with quality metrics
8. **Self-Tuning Optimization** — Dynamically adjust pipeline parameters via AIMD control
9. **Live Monitoring** — Real-time terminal dashboard of pipeline health

### 2.3 User Classes and Characteristics

| User Class | Description |
|-----------|-------------|
| **Pipeline Operator** | Runs and monitors the pipeline; configures `.env`; resolves CAPTCHAs |
| **Data Consumer** | Uses the final `dataset.jsonl` for AI/ML training |
| **Developer** | Extends or debugs pipeline stages; reads logs |

### 2.4 Operating Environment

- **OS:** Linux (primary), compatible with any OS supporting Docker
- **Python:** 3.10+
- **Docker:** Must be running for VJS functionality
- **Browser:** Google Chrome (for undetected-chromedriver Selenium automation)
- **Storage:** Minimum 5 GB free disk space for intermediate data and dataset

### 2.5 Design and Implementation Constraints

- Must use SQLite WAL mode to support concurrent read/write from multiple threads
- LLM API calls must respect rate limits via `KeyManager`
- No parallelism in SQLite write operations (serialized via `database_writer.py`)
- Docker must be available and the `synapse-judge` image must be pre-built
- Credentials must be stored in `.env` file, never hard-coded

## 3. System Features & Functional Requirements

### 3.1 Stage 1: Problem Ingestion (Scraper)

**Description:** Fetches all necessary raw data for a problem from Codeforces using a hybrid scraping strategy.

**Functional Requirements:**

| ID | Requirement |
|----|-------------|
| FR-1.1 | The system SHALL use `requests` (HTTP) for public-facing problem pages (statement HTML, time/memory limits, example test cases) |
| FR-1.2 | The system SHALL use an authenticated `undetected-chromedriver` instance to scrape source code from protected submission pages |
| FR-1.3 | The system SHALL scrape up to `N_REFERENCE_SOLUTIONS` (default: 5) top-rated accepted C++ submissions per problem |
| FR-1.4 | The system SHALL attempt to enrich example pretests using Codeforces' internal API by transferring browser session cookies |
| FR-1.5 | The system SHALL detect IP ban responses and raise an `IPBanException` to halt scraping |
| FR-1.6 | The system SHALL quarantine interactive problems (detected via HTML keyword scan) |
| FR-1.7 | The system SHOULD reuse browser instances (up to `MAX_BROWSER_USES=25` times) to avoid session overhead |
| FR-1.8 | The system SHALL support re-scraping to find a new reference solution when a problem fails analysis repeatedly |

### 3.2 Stage 2: Calibration

**Description:** Validates the scraped reference solutions (oracles) by compiling them in Docker and establishes a performance baseline.

**Functional Requirements:**

| ID | Requirement |
|----|-------------|
| FR-2.1 | The system SHALL compile each oracle using the Docker-based VJS (`compile_only` mode) |
| FR-2.2 | The system SHALL require at least `MIN_VIABLE_ORACLES` (default: 3) successful compilations to proceed |
| FR-2.3 | The system SHALL quarantine a problem if fewer than `MIN_VIABLE_ORACLES` oracles compile |
| FR-2.4 | The system SHALL run the primary oracle against pretests to calculate a `slowness_factor` |
| FR-2.5 | The system SHALL detect set-based output problems (PRESENTATION_ERROR) and set `checker_mode = 'set_based'` |
| FR-2.6 | The system SHALL save compiled oracle binary paths and validated pretests to `workspace.db` |

### 3.3 Stage 3: Analysis (Gemini LLM — Analyst)

**Description:** Sends batches of problems to the Gemini API to analyze oracle quality and produce canonical pseudocode.

**Functional Requirements:**

| ID | Requirement |
|----|-------------|
| FR-3.1 | The system SHALL send batches (default size: 5) of problems in a single API call to optimize throughput |
| FR-3.2 | The system SHALL preprocess C++ code before sending (strip comments, includes, boilerplate) |
| FR-3.3 | The system SHALL select and send the top 3 highest-quality oracle solutions per problem |
| FR-3.4 | The system SHALL parse the Gemini response as a structured JSON object containing `analysis` and `final_pseudocode` |
| FR-3.5 | The system SHALL handle partial batch success — successfully analyzed problems proceed, failed ones are quarantined |
| FR-3.6 | The system SHALL quarantine a problem if `analysis_try_count >= MAX_ANALYSIS_RETRIES` (default: 3) |
| FR-3.7 | The system SHALL transition a problem to `pending_rescraping` if retries are exhausted and `rescraping_attempts < MAX_RESCRAPING_ATTEMPTS` |
| FR-3.8 | The Gemini response SHALL include per-oracle quality ratings: `Excellent`, `Good`, `Fair`, or `Poor` |

### 3.4 Stage 4: Implementation (Groq LLM — Implementer)

**Description:** Sends pseudocode to the Groq (Llama) API to reconstruct a complete C++ solution.

**Functional Requirements:**

| ID | Requirement |
|----|-------------|
| FR-4.1 | The system SHALL call the Groq API with the problem HTML, pseudocode, and any VJS failure report |
| FR-4.2 | The system SHALL sanitize the LLM output to strip markdown formatting from raw code |
| FR-4.3 | The system SHALL quarantine a problem if `implementation_try_count >= MAX_IMPLEMENTATION_RETRIES` (default: 5) |
| FR-4.4 | Compile errors from VJS SHALL feed back to the Implementer for syntax correction |
| FR-4.5 | Logic/runtime errors from VJS SHALL feed back to the Analyst for algorithm correction |

### 3.5 Stage 5: Verification & Judging (VJS)

**Description:** Compiles and judges the AI-generated code inside a Docker sandbox against oracle-generated expected outputs.

**Functional Requirements:**

| ID | Requirement |
|----|-------------|
| FR-5.1 | The system SHALL run all compiled oracle binaries in parallel to generate "golden" expected outputs |
| FR-5.2 | The system SHALL determine consensus expected output via a tiered weighted-vote mechanism |
| FR-5.3 | Oracle weights SHALL be based on Gemini quality ratings: Excellent=4, Good=3, Fair=2, Poor=1 |
| FR-5.4 | The system SHALL attempt a second-tier recount with an adaptive threshold if the primary vote fails |
| FR-5.5 | The system SHALL quarantine a problem if consensus cannot be established |
| FR-5.6 | The system SHALL compile the AI-generated C++ code inside Docker with `g++ -O2 -std=c++23 -static` |
| FR-5.7 | Compilation failure SHALL route back to `pending_implementation` with the compiler stderr as the retry report |
| FR-5.8 | Runtime failure or Wrong Answer SHALL route back to `pending_analysis` with a detailed failure report |
| FR-5.9 | The system SHALL use `synapse.checker` to validate AI output against oracle output |
| FR-5.10 | On VJS success, `confidence_level` SHALL be set to 2 in `progress.db` |

### 3.6 Stage 6: Data Assembly

**Description:** Assembles the final golden record and writes it to the output dataset.

**Functional Requirements:**

| ID | Requirement |
|----|-------------|
| FR-6.1 | The system SHALL assemble a complete JSON record including: problem metadata, HTML statement, pseudocode, reference code, reconstructed code, pretests, code quality metrics |
| FR-6.2 | Code quality metrics SHALL include cyclomatic complexity (via `lizard`) and static analysis results (via `cppcheck`) |
| FR-6.3 | The assembled record SHALL be appended to `dataset.jsonl` |
| FR-6.4 | The system SHALL delete the problem's data from `workspace.db` after successful assembly |
| FR-6.5 | The system SHALL delete all temporary compiled oracle directories |
| FR-6.6 | The problem status in `progress.db` SHALL be set to `completed` |

### 3.7 Self-Tuning Optimizer

**Description:** A separate process that monitors pipeline health and dynamically adjusts operational parameters.

**Functional Requirements:**

| ID | Requirement |
|----|-------------|
| FR-7.1 | The optimizer SHALL run in its own process, independent of the main pipeline |
| FR-7.2 | The optimizer SHALL read pipeline state from `progress.db` every `OPTIMIZER_LOOP_DELAY_SECONDS` (default: 60s) |
| FR-7.3 | The optimizer SHALL detect IP bans and set `ingestion_worker_count = 0` for 2 hours (PANIC MODE) |
| FR-7.4 | The optimizer SHALL increase scraper delay by 0.5s per cycle when ingestion failure rate is high |
| FR-7.5 | The optimizer SHALL use an AIMD controller for `analysis_worker_count` to respond to API rate limits |
| FR-7.6 | The optimizer SHALL use a P-controller to maintain `TARGET_VJS_QUEUE_SIZE` (default: 20) |
| FR-7.7 | All optimizer actions SHALL respect a `OPTIMIZER_COOLDOWN_PERIOD_SECONDS` (default: 300s) between adjustments |

### 3.8 Live Dashboard

**Description:** A terminal-based monitoring interface for the running pipeline.

**Functional Requirements:**

| ID | Requirement |
|----|-------------|
| FR-8.1 | The dashboard SHALL display real-time queue sizes for each pipeline stage |
| FR-8.2 | The dashboard SHALL display live status of all worker threads (pool, problem ID, current stage) |
| FR-8.3 | The dashboard SHALL display current optimizer lever values |
| FR-8.4 | The dashboard SHALL display unicode sparkline graphs for VJS queue size, Analysis success rate, and Ingestion success rate |
| FR-8.5 | The dashboard SHALL refresh every 2 seconds using read-only DB access (WAL mode, no blocking) |

### 3.9 Key Manager & API Resilience

**Functional Requirements:**

| ID | Requirement |
|----|-------------|
| FR-9.1 | The system SHALL support multiple API keys for both Gemini and Groq services |
| FR-9.2 | The system SHALL track per-key rate limit windows and token usage |
| FR-9.3 | Rate-limited keys SHALL be placed in cooldown and another key selected automatically |
| FR-9.4 | Invalid keys SHALL be permanently marked and excluded from future use |
| FR-9.5 | A background `KeyHealthMonitor` thread SHALL periodically reset time-windowed rate limit counters |

## 4. Non-Functional Requirements

### 4.1 Performance

| ID | Requirement |
|----|-------------|
| NFR-1.1 | The pipeline SHALL process multiple problems concurrently using `ThreadPoolExecutor` per stage |
| NFR-1.2 | VJS oracle runs SHALL be parallelized using an inner `ThreadPoolExecutor` |
| NFR-1.3 | All SQLite write operations SHALL be serialized via the `db_writer` queue to prevent lock contention |
| NFR-1.4 | The orchestrator dispatch loop SHALL sleep 10s when jobs are active and 20s when idle |

### 4.2 Reliability & Fault Tolerance

| ID | Requirement |
|----|-------------|
| NFR-2.1 | The pipeline SHALL be fully resumable — stopping and restarting SHALL not cause data loss or duplicate processing |
| NFR-2.2 | All state transitions SHALL be atomic database operations to prevent partial updates |
| NFR-2.3 | Transient database lock errors SHALL be retried up to 5 times with exponential backoff |
| NFR-2.4 | Worker exceptions SHALL be caught, logged, and the problem transitioned to a `failed_*` state |
| NFR-2.5 | Browser instances SHALL be retired after 25 uses to prevent memory/stability degradation |

### 4.3 Security

| ID | Requirement |
|----|-------------|
| NFR-3.1 | All compiled and executed code SHALL run inside a Docker container with memory limits enforced |
| NFR-3.2 | Docker containers SHALL run as a non-root user (`--user uid:gid`) |
| NFR-3.3 | Code execution inside Docker SHALL use read-only volume mounts where possible |
| NFR-3.4 | API credentials SHALL be stored exclusively in `.env` files and never committed to version control |
| NFR-3.5 | The `synapse-judge` Docker image SHALL be a minimal, controlled environment |

### 4.4 Maintainability

| ID | Requirement |
|----|-------------|
| NFR-4.1 | All parameters SHALL be configurable via `config.py` (static) or `dynamic_config` table (runtime) |
| NFR-4.2 | Each pipeline stage SHALL be implemented as an independent, stateless worker function |
| NFR-4.3 | All significant pipeline events SHALL be logged to `process_history` table |
| NFR-4.4 | All performance metrics SHALL be logged to the `metrics` table |

### 4.5 Scalability

| ID | Requirement |
|----|-------------|
| NFR-5.1 | Worker pool sizes SHALL be dynamically adjustable at runtime via the `dynamic_config` DB table |
| NFR-5.2 | The system SHALL support up to `MAX_ANALYSIS_WORKERS=8` concurrent analysis workers |
| NFR-5.3 | The system SHALL support up to `MAX_IMPLEMENTATION_WORKERS=8` concurrent implementation workers |

## 5. External Interface Requirements

### 5.1 Codeforces API

- **Endpoint:** `https://codeforces.com/api/contest.status`
- **Method:** GET
- **Auth:** Public (for API), Browser session (for submission source code)
- **Rate Limiting:** Managed by scraper delay parameter (default: 2.5s between requests)

### 5.2 Google Gemini API

- **Model:** `gemini-2.5-pro`
- **Input:** Structured JSON batch prompt containing problem HTML + oracle C++ code
- **Output:** JSON with oracle quality analysis + pseudocode
- **Auth:** API key from `.env`

### 5.3 Groq API

- **Model:** `llama-3.3-70b-versatile`
- **Input:** Problem HTML + pseudocode + optional VJS failure report
- **Output:** Raw C++ source code
- **Auth:** API key from `.env`

### 5.4 Docker

- **Image:** `synapse-judge` (custom, built from `Dockerfile`)
- **Compile command:** `g++ main.cpp -o main -O2 -std=c++23 -static`
- **Execute:** `timeout <T> ./main` with stdin/stdout piped
- **Constraints:** `--memory=<limit>k`, `--ulimit stack=268435456`

## 6. System Constraints & Assumptions

### 6.1 Constraints

- The system is designed to run on a local machine with Docker daemon access
- Codeforces may require manual CAPTCHA solving during initial browser session setup
- The `synapse-judge` Docker image must be manually built before first run
- `progress.db` and `workspace.db` must be initialized via `create_database.py`
- DVC remote storage must be separately configured for dataset backup

### 6.2 Assumptions

- The operator has valid Codeforces credentials for accessing submission source code
- At least one valid Gemini API key and one Groq API key are provided in `.env`
- Google Chrome is installed on the host machine
- Docker Desktop is running
- The operator can monitor the dashboard and resolve PANIC MODE events

## 8. Pipeline State Machine

A problem transitions through these states in `progress.db`:

```
pending_ingestion
    │
    ▼ (ingestion_worker)
pending_calibration
    │
    ▼ (calibration_worker)
pending_analysis ◄───────────────────────────────────────┐
    │                                                     │
    ▼ (analysis_worker — batch)                           │ (VJS: logic/runtime failure)
pending_implementation ◄─────────────────────┐           │
    │                                         │           │
    ▼ (implementation_worker)                 │ (VJS:     │
pending_vjs                                   │  compile  │
    │                                         │  error)   │
    ├───────────────────────────────────────►─┘           │
    ├───────────────────────────────────────────────────►─┘
    │
    ▼ (vjs_worker — SUCCESS)
pending_data_assembly
    │
    ▼ (data_assembly_worker)
completed
    
    
At any stage → quarantined (unrecoverable failure)
At any stage → failed_<stage> (transient failure, will be retried)
pending_analysis → pending_rescraping → pending_ingestion (re-scrape loop)
```

## 9. Glossary

| Term | Meaning |
|------|---------|
| **Patient Resilience** | The design philosophy of handling long-duration failures gracefully |
| **N-Version Programming** | Using N independent oracle solutions to establish a ground truth |
| **Tiered Consensus** | Two-level voting system (weighted vote → trusted council recount) |
| **PANIC MODE** | Optimizer emergency state triggered by IP ban detection |
| **Quarantine** | Terminal failed state for problems that cannot be processed |
| **Slowness Factor** | Local machine speed multiplier applied to official time limits |
| **Checker Mode** | `strict` (exact match) or `set_based` (unordered match) for output validation |
