3.0 AGREED-UPON TECHNICAL ARCHITECTURE & PLAN

    Overall Strategy: A hybrid model where a local machine orchestrates the entire pipeline, outsourcing the heavy LLM reasoning to external APIs, and running the verification locally.

    A. Orchestrator & Ingestion (Local):

        A master Python script manages the end-to-end workflow.

        Uses the Codeforces API and respectful scraping to fetch problem data.

        Must be built to be resumable.

    B. Abstract Reasoning Layer (External APIs):

        LLM A (Analyst): The Google Gemini API free tier (e.g., Gemini 1.5 Flash/Pro) will be used for the complex task of analyzing code and context to generate pseudocode.

        LLM B (Implementer): The Groq API free tier (running Llama 3 or similar) will be used for the high-speed reconstruction of code from pseudocode.

        Critical Feature: The Python script must include robust error handling and exponential backoff to manage API rate limits gracefully.

    C. Verification & Judging Subsystem (VJS) (Local):

        Technology: Docker Desktop running a minimal Linux container to create a secure and consistent sandbox.

        Method: Functional Equivalence Testing. The script will compile and run both the reference and reconstructed code against all scraped public pretests, enforcing time and memory limits.

    D. Data Management & Workflow (Local):

        Storage Strategy: A "Process-and-Discard" workflow must be used to manage the 150GB storage limit. Intermediate files for a problem are deleted after it's successfully processed.

        Checkpointing: A local SQLite database (progress.db) will track the status of every problem (pending, completed, failed) to ensure the process is resumable.

        Final Dataset: The final data will be appended as new lines to a .jsonl file to handle large sizes efficiently. This file should be backed up to a free cloud service like Google Drive.

        Versioning: Git for all code; DVC for tracking the dataset.
